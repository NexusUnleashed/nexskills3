# Hot-path matching optimization

Status: proposed, not implemented
Date: 2026-08-29
Scope: `checkSkills` / `checkNpcs` in [`src/base/nexSkills.js`](../../src/base/nexSkills.js)

---

## Premise

`nexAction` was reworked to cut text-matching cost on the Nexus hot path, using
literal **prefix gating**, **first-character bucketing**, an **exact-string
downgrade**, and **lazily rebuilt indexes**. `nexSkills` runs on the same hot
path — once per visible game line — but was never given the same treatment.

The question this document answers: _does nexSkills use any of those techniques,
and which of them are worth adopting here?_

Short answer: it uses **none** of them, and the definition corpus turns out to be
close to a best case for them. A prototype measured **9.5x faster** with no
observable behavior change.

## How nexSkills is invoked

The per-line call site is not in this repo. It lives in the `eventStream3` `.nxs`
payload as a Nexus trigger named **"Master Skill Trigger"**:

```js
if (
  typeof nexSkills === "undefined" ||
  nexusclient.current_line.is_prompt ||
  nexusclient.current_line.gag
) {
  return;
}
nexSkills.checkSkills(nexusclient.current_line.parsed_line.text());
```

Consequences that shape everything below:

- `checkSkills` runs **once per non-prompt, non-gagged line**. Prompt and gag
  filtering already happens upstream, so there is no cheap pre-filter left to add
  outside nexSkills — pruning has to happen inside `checkSkills`.
- It receives a **plain string**, not the parsed-line object. The colour chunks
  exist on `current_line.parsed_line` but never reach nexSkills, so nexAction's
  `fg`/`bg` pre-filter has no analogue here without changing the trigger's call
  signature.
- It runs **synchronously inside `process_lines`**, so its cost is blocked
  rendering time during a burst.

## Method

All numbers below were produced against the real definition set, loaded out of
`src/base/` in Node with `GMCP` / `eventStream` / `nexusclient` stubbed. Timing
runs used 200,000 lines after a 10,000-line warmup, with two corpora:

- **5% match** — 1 in 20 lines is a line that a definition actually matches,
  generated by extracting the literal body of every fully-anchored `^...$`
  pattern.
- **0% match** — generic MUD output (room descriptions, says, vitals prompts,
  time-of-day messages) that matches nothing. This is the case that dominates in
  practice and the one worth optimizing.

Profile used for per-line counts: class `Occultist`, area `417` (the largest NPC
area, 139 NPCs).

Correctness was checked by running the current implementation and the prototype
side by side and comparing the resolved `(definition id, matchType)` pair.

## Findings

### 1. The current hot path is a flat linear scan

[`checkSkills`](../../src/base/nexSkills.js#L288-L320) walks all 354 action
definitions and, for each, calls `text.match()` for `firstPerson` (profession
permitting), `secondPerson`, and `thirdPerson` — then falls through to
[`checkNpcs`](../../src/base/nexSkills.js#L360-L390) for up to 139 more.

Per unmatched line, as Occultist in area 417:

| Work                                          | Count   |
| --------------------------------------------- | ------- |
| Action `firstPerson` regex (profession-gated)  | 82      |
| Action `secondPerson` regex (always)           | 180     |
| Action `thirdPerson` regex (always)            | 239     |
| NPC `firstPerson` regex                        | 138     |
| NPC `thirdPerson` regex                        | 85      |
| **Total regex executions**                     | **724** |
| `profession.includes()` array scans            | 708     |

Two secondary costs worth noting:

- The profession test at [`nexSkills.js:295`](../../src/base/nexSkills.js#L295)
  is two linear `Array.prototype.includes` scans **per action per line**.
- `GMCP.Char.Status.class.toLowerCase()` at
  [`nexSkills.js:289`](../../src/base/nexSkills.js#L289) allocates a string every
  line.

The area-NPC resolution is already cached
([`resolveAreaNpcs`](../../src/base/nexSkills.js#L338-L358)) and the match-time
clone in `evaluateText` is already deferred until a match is found. Those two are
the only existing optimizations, and neither addresses the scan itself.

### 2. The corpus is unusually well suited to gating

| Property                  | Value                      |
| ------------------------- | -------------------------- |
| Action definitions        | 354                        |
| NPC definitions           | 469 (28 areas)             |
| Total patterns            | 1250 (682 action, 568 NPC) |
| `^`-anchored              | **1201 (96%)**             |
| Case-insensitive (`/i`)   | **0**                      |
| Fully literal `^...$`     | 477 (38%)                  |
| Multi-line array patterns | 17                         |
| Non-regex patterns        | 29                         |

nexAction refuses to gate case-insensitive or unanchored patterns. Neither
disqualifier meaningfully applies here.

Gate lengths for the anchored set:

| Percentile | Literal prefix length |
| ---------- | --------------------- |
| p25        | 20                    |
| **median** | **62**                |
| p75        | 107                   |
| p90        | 138                   |
| max        | 333                   |

964 patterns carry a usable prefix (>= 5 chars). nexAction caps gates at 30
characters; a sweep of 12 / 30 / 60 / 200 showed 30 is already at the knee — a
longer cap costs nothing but buys nothing either, because `startsWith` fails on
the first differing character.

### 3. First-character bucketing is the weakest of the four techniques here

Bucket distribution over the 964 gated patterns:

```
A:320  Y:190  T:74  W:73  S:49  R:46  L:35  H:25  O:22  D:19  C:19
F:17  G:14  B:12  M:11  I:9  ":9  P:7  V:6  N:2  E:2  K:1  J:1  U:1
```

24 distinct buckets, but the distribution is badly skewed: `A` holds **33.2%**
(from `A <npc name> ...`) and `Y` holds 19.7% (from `You ...`). That is a much
worse spread than nexAction sees, and it means the bucket alone prunes far less
than the prefix gate does. It is still worth ~1.5x, but it should not lead the
work.

### 4. There is a gap nexAction does not cover

236 patterns have **no usable prefix** because they open with a capture group:

```
^(?<user>\w+?) charges quickly at (?<target>.+?), throwing \w+ massive form ...
^(?<target>.+?) grows paler as \w+ shadow grows more opaque\.$
```

This is essentially the entire `thirdPerson` family. nexAction never encounters
this shape, so it has no answer for it — but **228 of those 236** contain a
required literal substring of >= 8 characters (median 52, max 181) that can be
tested with `text.includes(substring)` before the regex runs.

This is the single highest-value technique for nexSkills, and it is the one that
has to be invented here rather than copied.

### 5. Measured results

Baseline, current implementation:

| Corpus   | Cost         |
| -------- | ------------ |
| 5% match | 54.8 us/line |
| 0% match | 54.9 us/line |

Prototype with all techniques, and ablation (0% match corpus):

| Configuration                         | us/line  |
| ------------------------------------- | -------- |
| Current implementation                | 54.9     |
| Structural cleanup only, no gating    | 33.5     |
| **All four techniques**               | **4.75** |
| ...minus first-char bucket            | 7.03     |
| ...minus substring gate               | 10.43    |
| ...minus prefix gate + substring gate | 12.10    |
| ...minus exact-string downgrade       | 4.76     |

Final prototype: **5.77 us/line** at 5% match, **4.74 us/line** at 0% match.

Regex executions fall from **724 to ~20 per line**.

Two results deserve emphasis:

- **The exact-string downgrade is nearly free — and buys nearly nothing** (4.75
  vs 4.76). Once gating runs first, almost nothing reaches the regex engine, so
  the downgrade has no work left to save. Include it because it is cheap, not
  because it moves the number.
- **Structural cleanup alone is worth 1.6x** (54.9 -> 33.5) before any gating.
  That is the per-class index and flattened entries removing the 708
  `includes()` scans and the property-chase per visit. It is independently
  worthwhile and lower-risk than the gating work.

### 6. Correctness

The prototype was cross-checked against the current implementation over
**25 classes x 12 areas x 479 lines = 143,700 comparisons**, comparing the
resolved `(definition id, matchType)` pair.

**0 disagreements.**

## Conclusions

1. nexSkills uses none of nexAction's hot-path techniques. The scan is flat and
   every pattern runs as a real regex on every line.
2. The corpus is close to a best case for gating: 96% anchored, no
   case-insensitive patterns, median usable prefix of 62 characters.
3. The achievable win is roughly **9.5x** (54.8 -> 5.8 us/line), verified
   behavior-preserving across 143,700 comparisons.
4. The ranking of techniques for _this_ corpus is not the same as for nexAction.
   Prefix and substring gating do the heavy lifting; bucketing is secondary; the
   exact-string downgrade is a rounding error.
5. A substring gate for capture-initial patterns is required to get the full
   win, and has to be written here — it does not exist in nexAction.

At a 1000-line burst (mapper walk, long `QL`, area scroll), this is roughly
**55 ms of blocked rendering today versus ~6 ms after**. That is the
user-visible symptom worth quoting to justify the work.

## Recommendations

Phased, ordered by value-to-risk. Each phase is independently shippable and
independently verifiable.

### Phase 1 — Structural cleanup (no gating)

Worth 1.6x on its own, and it builds the index that later phases hang off.

- Build a flat entry list at registry time: one entry per
  `(definition, matchType)` pair, carrying `{ def, kindIdx, order, kind, pattern,
exactText, gate, sub }`. Avoid the `e.c.gate` indirection — a flat object
  measurably beats a nested one in this loop.
- Replace the two `profession.includes()` scans with a **per-class index** built
  once and cached, keyed on the lowercased class, rebuilt only when
  `GMCP.Char.Status.class` changes. `firstPerson` entries for ineligible
  professions are then absent from the walk rather than skipped during it.
- Cache the lowercased class string alongside it so the per-line `.toLowerCase()`
  allocation disappears.
- Use a numeric `kindIdx` rather than a string `matchType` comparison inside the
  loop.

### Phase 2 — Prefix gate and substring gate

The bulk of the win (33.5 -> ~7 us/line).

- Port `analyzeRegexPattern` / `parseLiteralRun` from
  [`nexaction3/src/base/nexaction/patternCompilation.js`](../../../nexaction3/src/base/nexaction/patternCompilation.js).
  It already handles `SIMPLE_ESCAPES`, hex `\xHH`, and unicode `\uHHHH` /
  `\u{...}` decoding. Keep `MIN_GATE_LENGTH = 5` and `MAX_GATE_LENGTH = 30` — the
  sweep confirms 30 is at the knee.
- Add a **substring gate** for entries with no usable prefix: extract the longest
  literal run at paren-depth zero, bail entirely if the source contains `|`
  (alternation makes no literal required), and drop the final character if it is
  followed by `?`, `*`, or `{` (it is quantified, therefore optional). Require
  >= 8 characters. Apply as `text.includes(sub)`.
- Apply gates before the regex: `startsWith(gate)` if a prefix gate exists,
  otherwise `includes(sub)` if a substring gate exists.

### Phase 3 — First-character bucket

The remaining ~1.5x, and the phase that introduces the ordering invariant.

- `Map<gate[0], entry[]>` plus an ungated list, merged by `order` during the walk
  exactly as
  [`createHandler.js`](../../../nexaction3/src/base/nexaction/createHandler.js)
  does, so first-match-wins semantics are preserved.
- Build the NPC index per area, cached alongside the existing `resolveAreaNpcs`
  cache and invalidated with it.

### Phase 4 — Exact-string downgrade

Cheap, tidy, and worth almost nothing. Do it last or fold it into Phase 2.

- Fully literal `^...$` patterns become a `===` comparison. Note that
  [`processMatch`](../../src/base/nexSkills.js#L173-L188) reads `result.groups`,
  `result[0]`, and assigns `action.match = result` — a synthesized match must
  keep that shape. nexAction's `createStringMatch` is the reference, but it does
  not set `groups`; a fully literal pattern has no named groups, so `groups`
  being `undefined` is correct and the existing `groups?.user` optional chaining
  already handles it.

## Invariants and risks

- **Gating must never produce a false negative.** This is nexAction's stated rule
  and it carries over unchanged: when it is not certain that a literal is
  _required_, emit no gate. Preferring `gate: false` costs a little speed;
  getting it wrong silently drops a skill match, which is the worst failure mode
  this package has.
- **Alternation is the trap for the substring gate.** `(a|b)` means neither
  branch's literal is required. Bailing on any `|` in the source is crude but
  safe, and it is what produced 0 disagreements.
- **Quantified trailing characters.** In `abc?`, `c` is optional and must not
  enter the gate. Same for `*` and `{n,m}`.
- **Order must be preserved.** `checkSkills` returns the first match in
  definition order, `firstPerson` before `secondPerson` before `thirdPerson`.
  Bucketing splits that order across two lists; the merge walk restores it. No
  disagreement was observed without the merge, but definitions are not guaranteed
  mutually exclusive, so the merge stays.
- **Multi-line array patterns**
  ([17 of them](../../src/base/nexSkills.js#L203-L213)) read
  `nexusclient.current_block`. They cannot be prefix-gated on the current line
  alone in the general case; gate them on their _first_ pattern only, or leave
  them ungated. The prototype left them ungated.
- **`reaction` callbacks can rewrite `action.id`** (bladedance, occultism
  compel), which is why `finalizeCheck` compares against `eventActionId`. Index
  entries key off the definition, not the live id, so this is unaffected — but do
  not start caching anything derived from `action.id`.

## Out of scope

- **`fg`/`bg` pre-filtering.** nexSkills receives a string, not a parsed line.
  Adding it means changing the Master Skill Trigger's call signature in
  `eventStream3`, which is a cross-package change for a benefit the gating
  already captures.
- **Reworking the definition format.** All of this is derivable from the existing
  `patterns` objects at registry time. No definition file needs to change.
